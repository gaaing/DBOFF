# DBOFF 系统性开发地图

> 项目：Dragon Ball Offline（DBOFF）
> 主分支：`main`
> 引擎：Godot 4.7.2（用户提供）
> 原版资源基准：用户指定的 DBO_CT_TW 1.69 TW 客户端；包级/根目录完整性仍按审计证据确认
> 功能参考：OpenDBO-Core（代码、数据结构、协议与机制参考；不作为原版资源母库）
> 维护者：ChatGPT
> 最后更新：2026-11-02

---

## 1. 项目最终目标

完整还原原版 Dragon Ball Online 的游戏内容、机制、数据语义与实际行为，同时以现代、清晰、轻量、可维护的 Godot 架构实现。

- **还原目标不缩水：** 职业、角色成长、战斗、技能、装备、地图、地形、NPC、怪物、任务、剧情、物件、动画、交互、活动和社交等，以原版实际数据与行为为依据。
- **实现方式可现代化：** 可改进模块边界、资源管线、渲染、异步加载、缓存、存档、网络与工具链；不得借“现代化”之名删减原版玩法。
- **不逐行照搬旧缺陷：** OpenDBO-Core 用于理解和核实机制，不要求 Godot 代码照搬 C++ 类结构。
- **Local-first：** 单机核心玩法尽量本地运行；在线服务只承担身份、跨设备同步、在线协调、分发、权威校验等确有必要的职责。
- **完整性优先：** “有脚本”“可运行”“局部演示成功”都不等于系统完整。

## 2. 最高工作顺序

项目开发严格按以下顺序推进：

1. **修复当前已有实现**：先解决真实 Bug、错误数据映射、资源引用断裂、生命周期问题和不稳定行为。
2. **完整对齐原版源码与数据**：逐函数/逐流程检查 OpenDBO-Core 和原版客户端行为，覆盖字段、枚举、状态流、生命周期、边界条件、失败路径和数据关系。
3. **评价现有实现并提出更优方案**：比较当前实现、原版机制和 Godot 合适实现，评价正确性、复杂度、性能、内存、加载、耦合、扩展性和维护成本。
4. **优化实现**：保留正确设计；只有存在明确收益或修复必要时才重构。不得为重构而重构。
5. **逐步还原尚缺系统与内容**：每个系统继续执行“修复→源码对齐→方案评价→优化→验收”完整闭环。
6. **跨系统整合与全局验收**：验证真实游戏流程和系统交互，不以孤立单元通过代替完整体验。

任何系统不得跳过前四步直接堆新功能。若某系统完全不存在，则先完成原版机制调查和架构设计，再进入实现。

## 3. 每个系统必须执行的完整工作闭环

### 3.1 现状审计与修复
- 阅读当前系统所有相关 GDScript、场景、资源引用、数据文件及调用方/被调用方。
- 建立真实调用链、生命周期、数据流和依赖图。
- 重现并定位 Bug；检查空值、非法数据、重复调用、异步竞态、资源释放、边界坐标、异常路径。
- 修复根因，不叠加临时补丁；保留原版应有行为。
- 记录修复前后行为和验证证据。

### 3.2 原版源码与数据完整对齐
- 查阅 OpenDBO-Core 对应 C++、头文件、枚举、结构体、状态机、数据表加载和服务端处理。
- 必要时同时查阅 DBO_CT_TW 原版客户端资源/配置/表格，避免只凭 OpenDBO 的实现推断客户端表现。
- 追踪调用链，不只看同名类或注释。
- 对照字段类型、枚举值、默认值、单位、坐标系、索引、生命周期、事件顺序、状态迁移、错误处理和网络语义。
- 为每个机制建立映射：原版机制/源码位置 → DBOFF 当前实现 → 差异 → 缺失项 → 数据依赖 → 验证方式。
- 原版资料无法证明的部分明确标为待查，不臆造。

### 3.3 实现方案评价
每个系统都必须回答：
- 当前实现是否正确、完整、职责清晰？
- 是否存在硬编码、重复逻辑、隐式依赖、过度耦合、数据源分裂或临时补丁？
- 是否合理使用 Godot 4.7.2 的节点、资源、信号、场景、线程/Worker、渲染和文件系统能力？
- 是否有更简单、更快、更可靠或更易扩展的实现？
- 优化会否改变原版行为或造成数据兼容问题？
- 哪些部分应保留，哪些部分需要重构，理由和收益是什么？

不得仅因代码行数、类名或个人偏好评价架构。

### 3.4 优化与验收
- 先定义验收范围和成功条件，再实施优化。
- 覆盖正常路径、边界条件、失败路径、重复调用、资源缺失和跨系统交互。
- 运行验证需记录 Godot 版本、场景/操作、日志和结果。
- 验收未覆盖的内容保留为待验证，不得扩展“已验证”范围。
- 每轮更新本地图与进度文档，记录结论、证据、风险和下一步。

### 阶段 2：原版机制完整对齐
- 对每个系统建立原版机制清单和逐项映射。
- 检查客户端与服务端职责差异；Local-first 不代表忽略原版服务端权威规则。
- 检查全部相关表格、属性、枚举、资源、动画事件和协议字段。
- 对原版系统中的条件分支、限制、冷却、距离、状态互斥、失败结果和奖励规则逐项核对。
- 未确认机制不得以简化实现冒充完整复刻。

### 阶段 3：实现质量与性能优化
- 处理模块边界、依赖反转、数据缓存、异步加载、区块流送、资源复用和对象生命周期。
- 检查 CPU/GPU、内存峰值、磁盘 IO、加载时间和大世界稳定性。
- 检查 UI 缩放、分辨率适配、输入映射、可访问性和本地化。
- 建立数据版本、存档迁移、资源 manifest 与可重复构建流程。
- 每项优化记录基准、改动、收益和回归风险。

### 阶段 4：缺失原版系统逐步还原
- 以 S11 内容目录为索引，按原版数据和源码逐项还原副本、活动、龙珠、载具、宠物、变身、PVP、竞赛、公会等内容。

- 不以“入口按钮存在”或“静态展示”标记系统已还原。

### 阶段 5：整合与完整验收
- 从新账号开始，验证创建角色、进入世界、移动、战斗、成长、接任务、完成任务、物品获得/装备、地图切换、退出和继续游戏的完整闭环。
- 验证长时间运行、重复进出地图、资源释放、损坏存档恢复和异常数据处理。
- 分别验收离线核心体验与在线服务功能。
- 最终按原版功能目录列出：已验证、部分实现、未实现、受限/待资料；不使用单一百分比掩盖缺口。

## 8. 状态定义

每个系统/子机制只使用以下状态，并注明范围：
- **未调查**：尚未审查当前实现。
- **已发现实现**：确认代码/数据存在，未判断完整性。
- **存在问题**：已找到 Bug、差异或风险。
- **修复中**：当前正在处理已知问题。
- **基础功能稳定**：限定基础流程已验证，尚未完成原版全量对齐。
- **原版对齐中**：正在逐项对照原版机制。
- **优化中**：基于审查结果改进实现。
- **部分还原**：部分原版机制已实现，缺口明确。
- **已验证（限定范围）**：代码、数据、原版对照和运行证据覆盖指定范围。
- **待扩展**：基础实现已验证，仍有原版内容或边界未覆盖。

不允许使用“100% 完成”“完美”或笼统百分比替代上述状态。已验证必须附上范围和证据。

### Antigravity
- 在用户本地执行只读扫描、收集完整文件、检查引用、运行 Godot、回传日志和复现证据。
- 依据用户分配的任务修改代码；修改后提供完整 diff/文件和测试结果供独立审查。
- 不擅自扩大修改范围，不删除、不自动 commit/push。
- 不与 ChatGPT 同时修改同一系统的同一核心文件。

### 协作约束
- 每轮明确唯一的核心文件修改负责人。
- 只读审查与代码修改分开；先确定根因和方案再修改。
- 任何新情报先记录来源与证据等级，再更新进度。
- 任何文档更新不得将未经验证的报告声明提升为事实。

1. 保持 Godot 工程可直接运行，先建立可重复的开发运行/导出基线；不得让启动器成为进入客户端或验证核心玩法的前置条件。
2. 先审查 DBOFF 当前网络相关脚本、project.godot、配置与调用方，并读取 dbo-web 当前 Markdown、Worker 路由和部署配置。
3. 设计统一客户端网络层：环境/端点配置、请求封装、会话令牌生命周期、错误模型、超时、断线与重试、版本兼容和离线降级。接口必须基于现有服务端实现和协议证据，不臆造 endpoint。
4. Cloudflare 第一批只接开发所需的最小闭环：健康/版本探测、登录/会话验证/登出、权限读取及必要的服务器配置；先验证认证与失败路径。

### 11.6 OpenDBO 原版登录协议初步映射（2026-11-02）

已锁定 OpenDBO-Core master HEAD：23cb305a6cf20048fec75595a8fa1ee2f1a0e83d（2026-10-29）。初步源码证据显示，原版客户端通过 TCP 二进制协议分别连接 AuthServer、CharServer、GameServer；MasterServer 在服务端内部协调登录/迁移与临时 AuthKey，QueryServer 负责数据库访问。它不是一组 HTTP API，也不是 WebSocket JSON 协议。

基础流程：
1. 客户端连接 AuthServer，发送 UA_LOGIN_REQ（账号名、密码字段、客户端版本、MAC）；AuthServer 校验版本、账号状态/密码、连接限制、CharServer 可用性与在线重复登录，并通过 MasterServer 做在线状态协调。成功的 AU_LOGIN_RES 携带 accountId、AuthKey、lastServerFarmId、服务器列表和 GM/开发权限字段。
2. 客户端连接选定 CharServer，发送 UC_LOGIN_REQ（accountId、AuthKey、serverFarmId）。CharServer 将 CM_LOGIN_REQ 转发给 MasterServer 验证 AuthKey；之后客户端通过 CharServer 请求角色数据、创建/删除/重命名角色。
3. 客户端发送 UC_CHARACTER_SELECT_REQ（charId、serverChannelId）。CharServer 校验角色归属、服务器/频道状态、可见性、锁定和负载，再通过 MasterServer 生成新的迁移 AuthKey。CU_CHARACTER_SELECT_RES 返回 charId、AuthKey、GameServer IP 和端口。
4. 客户端连接指定 GameServer，发送 UG_GAME_ENTER_REQ（accountId、charId、AuthKey、tutorial flag）。GameServer 再向 MasterServer 发送 GM_LOGIN_REQ 验证 AuthKey 和账号/频道归属；验证通过后才完成游戏进入响应和后续世界加载。

协议结构初步确认：NtlPacket.h 定义 4 字节基础头（15-bit packet length、1-bit encrypt 标志、16-bit sequence）；数据体以 16-bit opcode 开始。NtlPacketCommon.h 的协议结构与相关 packet header 使用 packed C/C++ struct。实现 Godot 适配器前必须继续核对完整帧长度语义、字节序、编码/加密、连接生命周期、超时和重连。

**账号桥接是当前关键未决项：** dbo-account-api 使用 Cloudflare D1 账号与 session_token；OpenDBO AuthServer 则从自己的账号数据库查询账号记录，并在登录成功后由 MasterServer 体系发放原版 AuthKey。Cloudflare session_token、OpenDBO 数字 accountId 和原版 AuthKey 是不同凭证/标识，不能直接互换。必须设计明确的账号映射或受信任的服务端令牌交换，不得把 Cloudflare session_token 填进原版 AuthKey 字段，也不得让 Godot 客户端自行伪造 AuthKey。

### 11.9 Doll-first 共斗与真人联机边界（2026-11-02）

用户确认：DBOFF 默认组队由本地 Doll 组成，不需要联网。Doll 从玩家存档生成，可来自自己的存档，也可来自其他玩家的存档；原版大多数共斗/对战行为原则上改为与 Doll 进行，不默认要求真人玩家在线。

开发顺序：
1. 完成本地存档可靠写入与运行时状态快照，每 60 秒本地保存。
2. 在 Godot 客户端内接账号注册/登录/session check/logout，且离线启动不受影响。

# DBOFF AI Development Rules

> 本文档由 ChatGPT 为当前 DBOFF 新项目建立。它是本项目 AI 协作时唯一采用的开发规则基准；仓库中其他历史报告不得覆盖本文规则。

## 1. 项目现状判断原则

1. 不将历史报告、进度表、勾选框、百分比或“已完成”措辞视为实现证据。
2. 历史 Markdown 仅可作为线索，必须回到当前代码、数据和 OpenDBO-Core 对照确认。
3. 不因脚本存在、场景可打开、无编译错误或单次演示成功，就判定一个功能完整。
4. 未经完整代码审查、数据核对和实际行为验证，不使用“完成”“完美”“完全对标”等结论。
5. 用户明确提供的当前状态可作为项目状态输入，但必须标注为“用户报告”，不得伪装成独立验证结果。
6. 每个系统分别记录：未检查、已发现代码、部分实现、存在问题、待验证、已验证范围。不能用一个笼统完成率代替。

## 2. 工作前置要求

1. 开始 DBOFF 工作前，先阅读本文件和 ChatGPT 编写的 `docs/AI_WORK_PROGRESS.md`。
2. 再读取与当前任务相关的源代码、场景、数据文件和 OpenDBO-Core 参考实现。
3. 检查 GitHub 时，区分“仓库未上传”和“本地不存在”。不得将前者说成后者。
4. 明确列出完成当前分析所缺少的文件、数据、代码或运行证据。
5. 若证据不足，明确说明未知项，不根据旧报告补齐事实。

## 3. 证据等级

按以下顺序记录结论，并注明来源：

- **A：当前代码/数据证据**：已读取当前分支的具体文件和相关实现。
- **B：OpenDBO-Core 参考证据**：已读取对应原版源码或数据结构。
- **C：运行行为证据**：有用户提供的日志、录屏、复现步骤或实际运行结果。
- **D：用户报告**：用户对当前进度、Bug 或外部修复工作的描述。
- **E：历史文档线索**：仓库旧报告中的说法，尚未被当前证据验证。

高等级证据不能被低等级文档声明覆盖。用户报告可以作为当前工作状态，但不等于代码已验证。

## 4. OpenDBO 对照规则

1. OpenDBO-Core 是原版机制和数据语义的参考，不将旧项目现有实现视为正确标准。
2. 对照时指出具体原版源码/结构、当前 Godot 对应实现、缺失机制、行为差异和所需数据。
3. 不只比较类名或文件名；必须比较状态流、数据字段、生命周期、边界条件和实际行为。
4. 不将“存在一个简化替代实现”描述成“已复刻原版功能”。
5. 对原版机制不清楚的地方，标注待查，不臆造。

## 5. 重构与代码交付约束

1. 当前阶段以清理旧代码、恢复清晰架构、逐系统对照 OpenDBO 为主。
2. 优先消除重复职责、隐式依赖、硬编码、临时补丁和不一致的数据路径；避免只为消除单个表面 Bug 而叠加补丁。
3. 未经用户明确授权，不直接修改项目代码、场景、资源或配置，不删除文件，不提交或推送代码。
4. 用户要求代码时，在聊天中提供完整代码或明确的修改片段，并说明目标路径和依赖。
5. 只读检查时保持只读，不额外生成测试文件或污染项目目录。
6. 不将 Antigravity 或其他工具声称已完成的修复视为事实；需读取修改后的文件和对应证据。

## 6. 文档维护

1. 本文件与 `AI_WORK_PROGRESS.md` 是 ChatGPT 维护的项目基准文档。
2. 新情报先区分来源和证据等级，再更新进度文档。
3. 历史报告不得自动复制为当前事实；如需引用，明确标为“历史报告声称，未核实”。
4. 每次更新记录日期、变更内容、依据和未解决问题。
5. 不在缺乏证据时将待办改为完成。

## 7. 当前阶段的完成定义

任何系统只有在以下方面有明确证据后，才可在限定范围内标记为已验证：

- 关键代码路径已审查；
- 必要数据与字段已核对；
- 对应 OpenDBO 机制已比较；
- 关键正常流程、边界情况和失败路径有验证证据；
- 已知 Bug 和未实现部分已明确列出。

“已验证”只覆盖实际检查的范围，不等于整个系统完美或没有 Bug。

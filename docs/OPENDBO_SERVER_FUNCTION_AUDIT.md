# OpenDBO 服务端职责盘点与 DBOFF 去中心化评估

> 日期：2026-11-02
> 参考：OpenDBO/OpenDBO-Core 当前 master；README 与对应服务器 packet/session 源码。
> 目的：列出原版服务器实际承担的职责，再决定 DBOFF 哪些功能本地化、P2P 化或保留可选服务器。
> 证据边界：本文件是第一轮职责清单，不代表每个子系统已逐函数审计，也不表示 DBOFF 已实现这些功能。

## 1. 用户本轮确认的产品方向（证据 D）

- 好友、公共大厅、组队目前均未决定采用服务器方案；要求优先寻找完全不依赖中心服务器的实现。
- OpenDBO 原版服务器功能必须先明确列出，再逐项决定是否需要服务器；用户预计最终只有极少数功能继续依赖服务器。
- 因此不得预设好友、公共大厅、组队必须由 Cloudflare Worker 或长期在线游戏服务器提供。
- 继续坚持 Local-first：离线单机流程不能因在线服务不可用而失效。

## 2. OpenDBO-Core 服务器进程清单（证据 B）

OpenDBO-Core README 的服务器目录表明确列出六类服务：AuthServer、CharServer、ChatServer、GameServer（每个频道一个进程）、MasterServer、QueryServer；README 特别说明 QueryServer 是唯一直接访问数据库的服务器。

| 服务 | 原版职责（第一轮） | DBOFF 初步判断 |
|---|---|---|
| AuthServer | 账号密码登录、账号状态/封禁/连接限制检查、客户端版本检查、登录阶段认证；与 MasterServer 协调账号在线状态，向客户端返回账号标识、初始 AuthKey、服务器列表及 GM/开发权限信息 | DBOFF 本地离线启动不需要；Cloudflare 账号仅作为云存档身份入口。只有明确要兼容原版在线服务器时才研究桥接 |
| CharServer | 角色列表/加载、创建、删除/恢复、重命名、角色归属与槽位校验；选择角色、选择频道并请求迁移到 GameServer | DBOFF 角色生命周期可以本地化；角色选择不应被原版 CharServer 绑定 |
| MasterServer | 服务端内部协调：服务器注册/状态、账号在线状态、AuthKey 校验/签发、AuthServer/CharServer/GameServer 之间的认证和迁移协调 | 属于原版服务集群控制面；若 DBOFF 不接原版集群，则无须复刻为独立服务器 |
| QueryServer | 唯一直接访问原版数据库的服务；承接其他服务的持久化查询/写入 | DBOFF 可用本地存档/本地数据库替代；Cloudflare 只负责云备份，不必照搬 QueryServer |
| GameServer（每频道进程） | 游戏世界运行时和服务端权威：进入世界、角色状态、移动同步、攻击/技能、物品/背包/装备、商店/银行/交易、任务、NPC/怪物交互、传送、队伍/副本、活动、PVP/竞赛等大量游戏请求处理 | 单机模式应在 Godot 本地实现；多人合作可评估由房主承担权威模拟，而非先建中央 GameServer |
| ChatServer（README 中的社区/聊天服务） | 聊天与社区功能；已读源码可见 Say、Shout、Whisper、Party Chat、Guild Chat、Trade Chat、Find Party Chat；还承担公会邀请/响应、成员管理等社区操作，并访问 QueryServer 持久化公会数据 | 普通聊天可 P2P；公会/跨设备持久化与全球广播若保留，需要另行设计分布式或可选节点，不应默认强制中心服务器 |

注意：以上是职责层面的首轮分类。OpenDBO 代码中还存在服务器内部通信与跨服务 packet，不应把每个 packet 都误认为玩家可见功能。

## 3. GameServer 实际承载的功能范围（证据 B）

已读取 `DboServer/Server/GameServer/PacketGameServer.cpp`，文件约 645 KB，提取到 309 个 `CClientSession` 请求处理函数。下列按处理函数名称和源码入口归类，属于已观察到的功能面，不代表每项逻辑均已深入审计：

### 3.1 角色与世界生命周期
- 游戏进入、进入世界、加载完成、角色准备、离开游戏、退出角色、切换频道/服务器、传送、复活、绑定点。
- 移动、飞行移动、方向/位置同步、跳跃、坠落、跟随移动、冲刺、坐下、战斗姿态。

### 3.2 战斗与角色能力
- 攻击开始/结束、技能请求、技能学习/升级/重置、HTB、RP、Buff、变身取消、目标选择、击倒恢复。
- 宠物/吉祥物技能与动作、载具驾驶、属性/状态变化。

### 3.3 物品、装备与经济
- 背包移动/堆叠/删除、商店买卖、银行、现金商店、私人商店、拍卖行、邮件附件、交易。
- 装备升级/修理/识别/封印/拆解/选项变更/时装宝石镶嵌、骰子、拾取、掉落。
- 货币、龙珠奖励、Hoi-Poi 制作、活动商店、物品兑换。

### 3.4 任务与世界内容
- 任务放弃/分享、Trigger System 执行、任务物件访问、任务状态更新。
- NPC/对象交互入口、传送点、快速传送、战争迷雾、世界地图状态。
- TimeQuest、动态副本、Dragonball Scramble、Budokai、Dojo/Dojo War、排名战等活动入口。

### 3.5 社交与多人玩法
- 创建/解散队伍、邀请/响应、离队、队长变更、踢出成员、队伍目标分享、战利品分配、骰子、队伍副本难度和匹配。
- 公会创建、邀请、银行、功能、标志、名称、道场与竞赛相关操作。
- 邮件、拍卖行、私人商店、玩家交易等跨玩家交互。

结论：原版 GameServer 不只是一个“移动同步服务器”，而是承载了大量游戏规则与权威状态。DBOFF 若做完整离线复刻，这些规则仍然要存在，但它们可以是本地 Godot 系统，不代表必须继续依赖远端 GameServer。

## 4. ChatServer 源码已确认的功能

已读取 `DboServer/Server/ChatServer/PacketChatServer.cpp` 与 `ClientSession.cpp` 的相关代码：
- 进入 ChatServer 时携带 accountId 与 AuthKey，并验证 AuthKey。
- Say / Shout：按频道、世界和距离向附近玩家广播。
- Whisper：按角色名查找在线目标，并检查黑名单。
- Party Chat：按 PartyID 广播。
- Guild Chat：向公会成员广播。
- Trade Chat 与 Find Party Chat：全服/跨频道广播，并进行等级、冷却、静音和 spam 检查。
- 公会邀请响应、解散、离会、踢人、任命副会长、修改公告等操作由 ChatServer 处理，并将持久化请求交给 QueryServer。

该源码范围没有证明好友列表/好友在线状态的全部职责都在 ChatServer；好友系统需要继续查找 opcode handler、packet 定义及 GameServer/ChatServer 两端调用链。

## 5. 无中心服务器方案的可行边界

| 功能 | 完全无中心服务的可行方案 | 限制/代价 |
|---|---|---|
| 好友名单 | 本地保存好友公钥/身份指纹；通过二维码、邀请码或玩家互相交换连接信息添加 | 无法自动获知好友是否在线；跨设备好友列表需通过用户自行导出/导入或云存档同步 |
| 私聊 | 直接 P2P 加密消息 | 双方必须同时可达；离线消息不能由不存在的服务器代存 |
| 组队 | 房主创建会话，成员通过 LAN 发现、手动地址/端口或分享邀请信息直连 | NAT/CGNAT 可能阻断直连；房主掉线会影响队伍 |
| 合作战斗 | 房主权威模拟（listen-host）；其他成员发送输入并接收状态快照 | 房主性能/网络成为瓶颈；房主作弊风险；需要预测、插值、重连和状态校验 |
| 公共大厅 | LAN 房间广播；玩家自建公开房间/社区节点；或分布式发现协议 | 全球公共目录需要可发现性；没有在线节点/目录/中继时，陌生玩家无法自动相互发现 |
| 在线状态 | 好友之间直接探测或通过最近一次互相连接信息推断 | 不能获得全局在线人数或准确在线状态；离线时无权威 presence |

### 5.1 需要区分的“无服务器”
- **无游戏逻辑中心服务器**：可以通过房主权威 P2P 实现合作战斗。
- **无中心账号/大厅服务**：可以用本地身份、公钥、邀请码和玩家自建目录，但会牺牲自动发现、离线消息和全局状态。
- **完全无任何第三方基础设施**：只能保证 LAN、手动公网直连/端口转发等路径；不能保证所有 NAT 环境下跨互联网互连。
- STUN 需要可访问的映射发现服务；TURN 需要中继服务。因此若采用它们，就不再是“完全不依赖任何服务”。

## 6. 初步拆分建议（尚未由用户批准为最终方案）

### 必须本地化
- 账号之外的本地角色生命周期、世界、移动、AI、战斗、任务、背包、装备、成长、NPC、掉落和单机活动。
- 本地设置、本地好友簿、本地队伍状态与单机模拟。

### 可 P2P / 房主模式
- 邀请、好友直连、私聊、队伍成员状态、合作战斗、共享目标、有限范围的交易/互动。
- 对多人有共享经济影响的交易、掉落归属和奖励结算，需要明确房主信任模型；P2P 并不能自动提供防作弊。

### 可能需要可选节点或服务器的功能
- 跨玩家全局公共大厅/房间目录、离线消息、全局在线状态、全局排行榜、跨设备共享公会状态、反作弊权威验证。
- 这些功能应先评估是否值得保留；不应为了复刻原版而自动实现。

## 7. 当前缺少的源码与证据

- MasterServer 全部注册/路由/AuthKey 生命周期和失败处理的完整调用链。
- QueryServer 各类数据库查询/写入的完整 packet handler 与表结构映射。
- AuthServer 密码验证、密码哈希/编码和账号状态边界。
- ChatServer 好友系统的完整 packet/handler 位置，以及好友添加、删除、在线状态、黑名单和跨频道同步机制。
- GameServer 队伍、匹配、交易、拍卖、邮件、公会、PVP、Budokai、Dojo War、TimeQuest 等系统逐函数服务端权威校验与数据写入路径。
- DBOFF 当前好友/大厅/组队实现文件（若存在）及用户对多人功能最终范围的决定。

## 8. 后续审计顺序

1. 先逐系统完成 OpenDBO 服务端职责矩阵：玩家可见功能、权威规则、持久化数据、跨服务依赖、断线行为。
2. 为每项标记：本地化、P2P、可选服务器、暂不实现/移除候选。
3. 优先审查 ChatServer 好友/公会/在线状态、GameServer 组队/匹配/交易等社交边界。
4. 再审查 MasterServer / QueryServer，确认哪些功能真正依赖中心协调与数据库。
5. 根据用户确认的保留范围，才设计 DBOFF 网络层；不要先写一个大而全的网络框架。

## 9. 本轮结论

- 好友、公共大厅、组队不再预设必须使用 Cloudflare 或中心游戏服务器。
- OpenDBO 六类服务及 GameServer/ChatServer 第一轮功能面已列出；需要继续逐函数审计，不能据此宣称清单完整。
- 本轮只读 OpenDBO-Core / DBOFF Markdown，并记录设计方向；没有修改 Godot 代码、OpenDBO 源码、Cloudflare Worker、D1 或 R2。

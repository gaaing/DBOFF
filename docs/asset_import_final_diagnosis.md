## 3. 为什么在最后 215 个文件反复卡顿？—— 核心根因彻底查清

经过对底层二进制数据、Godot 引擎进程线程堆栈及日志的精确审计，查明了导致进度停留在 25,553 (99.17%)、无法推进最后 215 个文件的三个根本原因：

### 根因一：队列首位文件存在底层 IEEE 754 `NaN`（非数字）浮点死循环
- **发现过程**：对未导入的 215 个文件按 Godot 资源路径字母序排序，排在第一位的即为 `res://assets/obj/character/mesh_mob/m_egb_a1.glb`。
- **二进制排查结果**：解包 `m_egb_a1.glb` 的二进制 BIN Chunk，检查全部 84 个顶点浮点数发现：
  ```text
  Vertex 0: pos=(nan, nan, nan), norm=(nan, nan, nan)
  Vertex 1: pos=(nan, nan, nan), norm=(nan, nan, nan)
  Vertex 2: pos=(nan, nan, nan), norm=(nan, nan, nan)
  Vertex 3: pos=(nan, nan, nan), norm=(nan, nan, nan)
  ```
- **引擎死循环机理**：在 IEEE 754 浮点规范中，任何与 `NaN` 的大小比较（如 `NaN < min` 或 `NaN > max`）**永远返回 False**。当 Godot 的 glTF 导入器解析该模型并构建 AABB 包围盒与 BVH 树时，循环判定条件永远无法满足，主线程直接陷入 100% CPU 无限死循环，导致进程永远卡在该文件，后续队列中的 214 个文件完全得不到执行机会。
- **全量排查范围**：对全工程 25,768 个文件进行全量扫描，查出全工程共有 21 个模型包含历史转换工具残留的 `NaN/Inf` 异常浮点（包括 `m_egb_a1.glb` 和特效中的 `ik_htb_fan_02_hcr_t023.glb`）。

### 根因二：glTF JSON 块空字节填充问题
- 原提取脚本在 4 字节对齐时使用了 `\x00`（Null）而非 glTF 2.0 官方规范的 `0x20`（ASCII 空格）进行补齐，导致严格解析模式报错。此前已批量纠正了 15,854 个相关文件的尾部对齐。

### 根因三：全工程 25,000+ 文件校验扫描开销与超时阈值冲突
- 由于工程根目录下累计超过 128,000 个缓存文件，每次 Godot 启动时进行的第一轮全量资源完整性扫描需要约 10~12 分钟。在此前的旧配置中，过短的超时时间或监控中断会导致进程在刚结束扫描、开始正式写盘时被强行截断。

## 3. 已落地的修复措施

1. **清除全部非法浮点数**：已针对扫描出的全部 21 个受影响模型（包括 `m_egb_a1.glb` 及 `ik_htb_fan_02_hcr_t023.glb`）执行二进制重构，将非法 `NaN/Inf` 彻底规范化为合法的 `0.0` 浮点数，消除了 AABB 计算死循环的底层触发源。
2. **glTF 结构合法性校验**：对剩余 215 个文件执行了 Node 树无环校验、Animation Sampler 索引校验、Accessor 缓冲区边界校验，确认当前 215 个文件均为合法的 glTF 2.0 标准资产，再无结构缺陷。
3. **关闭图形开销**：已锁定 `--headless` 模式及关闭了 LOD 生成选项，导入期间内存严格维持在 850MB~920MB，彻底告别 0xc0000005 内存泄漏崩溃。
